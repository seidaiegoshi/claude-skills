# コメントを簡潔に保つ

コメントを書こう・残そうとしている。その手が止まったこの瞬間が、このスキルの出番。

## なぜ簡潔さが大事か

コメントは**コードと一緒に腐る**。コードが変わってもコメントは自動では追従しない。だから「コードを読めば分かること」をコメントに書くと、いずれコードとズレて**嘘をつくコメント**になる。読み手はコメントとコードのどちらを信じるか迷い、検証コストを払う。一方で**書いた本人の意図・制約・回避策**はコードのどこにも残らない情報なので、消えると将来同じ罠を踏む。

さらにエージェント作業では、冗長なコメントが**次のターンで自分自身の入力**になる。ノイズを書くほど後続の判断が鈍る。

だから方針は一つ:**「なに」を消し、「なぜ」を残す。**（docstring だけは例外 → 後述）

## 1 行ごとの判断テスト

コメントを書く / 残すか迷ったら、自分に問う:

> **「このコメントを消したら、コードだけから読み取れない情報が失われるか?」**

- **失われない**（処理内容の言い換え、自明な説明）→ **書かない / 消す**。
- **失われる**（なぜそうしたか、なぜこうしないのか、外部の制約、ハマりどころ）→ **残す。ただし 1 行に圧縮。**

「失われる」と即答できないなら、たいてい「なに」コメント。消してよい。

## 行数の上限

**1 コメント 1 行が既定。2 行は例外、3 行以上は禁止。**

「1〜2 行まで OK」を常用上限として扱わないこと。2 行目を足す前に必ず「1 行目だけで通じないか」を確認する。上限は許可枠ではなく非常口。

## 残す（価値がある）

意図・制約・回避策・落とし穴。コードを読んでも**理由**は分からないもの。

```
# nullable FK の LEFT OUTER JOIN だと select_for_update() を PG が拒否するため主テーブルに限定する。
```
```
// 0 番目はヘッダ行なので集計から除外する（CSV 仕様）。
```
```
# 外部 API が稀に 200 で空ボディを返すので、ここで明示的に検査する。
```

これらは消すと「なぜこの不自然なコードなのか」が永久に分からなくなる。

## 削る（価値がない）

コードを読めば分かる処理内容の言い換え。関数名・変数名・型シグネチャで既に語られていること。

```
# ユーザーを ID で取得する     ← get_user_by_id() を読めば分かる
user = get_user_by_id(id)

# 合計に税額を足す             ← total += tax を読めば分かる
total += tax

// ローディング状態を true にする   ← setLoading(true) のまま
setLoading(true)
```

区切り線・装飾・`// --- ここから処理 ---` のような見出しコメントも、関数分割で代替できるなら削る。

思考過程の実況（「まず A して、次に B する」）、変更の経緯（「以前は X だったが Y に変えた」）も書かない。経緯はコミットメッセージへ、恒久的な規約はプロジェクトのドキュメントへ。**同じ情報を 2 箇所に置かない。**

## docstring は例外（ただし短く）

docstring は API としての説明責任を負うので、**行コメントと違って「何を」も残す**。機械的に「なに」を削って役割説明まで消さないこと。

**構成: 概要 1 行 + 理由 1〜2 行。**

- 概要（何を）: その関数・クラスの役割を 1 行。
- 理由（なぜ）: 意図・制約・使い分けが非自明なときだけ 1〜2 行足す。
- 例外は**公開 API・サービス関数の仕様列挙**のみ。その場合も 1 項目 1 行の箇条書きに収める。

**docstring から削るもの:**

- 型シグネチャの言い換えにすぎない `Args:` / `Returns:`（`user_id: int` を「ユーザー ID（整数）」と書き直すだけのもの）
- 実装手順の逐次解説（「1. 検証する 2. 保存する 3. 通知する」）→ 処理ステップの非自明な理由は、**その行の行コメント**に置く方がコード変更時にズレにくい
- 呼び出し例・使用例（テストが果たす役割）
- 関数名の言い換えだけの 1 行（`def save_user()` に「ユーザーを保存する」）→ 概要が名前と同義なら docstring ごと不要

```python
def consume_for_order(order, quantity):
    """注文の工程投入で在庫を引く。

    在庫不足でも完了はブロックせず、不足分を adjustment で補填してから引く。
    """
```

## コメントより先に、命名と分割

コメントを足したくなったら、まず**そのコメントが不要になる書き方**を探す。

- 説明用コメント → **意図を表す関数名・変数名**に置き換える（`# 期限切れを除く` より `exclude_expired()`）。
- ブロックを説明するコメント → その**ブロックを関数に切り出す**と名前が説明になる。
- マジックナンバーの説明 → **名前付き定数**にする。

コメントは「命名と構造では表現しきれない理由」を補う最後の手段。最初の手段ではない。

## 既存コードのコメントを整理するとき

「コメントを減らして / 整理して」と頼まれた、または自分の変更でコメントが増えたら:

1. **変更したコードのコメントに絞る**（指示がない限り、無関係な箇所まで広げない）。
2. 各コメントに上の**判断テスト**を当てる。「なに」は削除、「なぜ」は残して 1 行に圧縮。
3. 削れるが理由情報を含むものは、**コメント削除＋命名/分割で表現**できないか先に検討する。
4. 3 行以上の解説コメント・5 行以上の docstring は赤信号。本当に必要か・もっと短くできないかを必ず見直す。
5. **コードの挙動は変えない**。コメントの削除・圧縮と、それに伴う命名改善だけに留める。挙動を変える提案は分けて伝える。

## ありがちな言い訳（に流されない）

| 思考 | 実際 |
|------|------|
| 「丁寧な方が親切」 | 自明なコメントは読む手間を増やすだけ。コードが一次情報。 |
| 「後で誰かが分からなくなるかも」 | 分からなくなるのは"なぜ"。"なに"は読めば分かる。 |
| 「とりあえず書いておく」 | 腐って嘘になる負債を仕込んでいる。 |
| 「TODO だから残す」 | 理由・条件のない TODO はノイズ。何を・なぜ・いつを 1 行で。 |
| 「docstring は書くものだから」 | 名前の言い換えだけの docstring は削る対象。役割か理由を足せないなら不要。 |
| 「レビュアーのために説明を厚く」 | レビューで要る説明は PR 本文へ。コードに残すのは将来の読み手に要るものだけ。 |
