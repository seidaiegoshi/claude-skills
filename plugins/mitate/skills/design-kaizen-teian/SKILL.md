# UI 批評 → HTML 提案

稼働中の Web 画面を**実際に開いて観察・実測し**、UX/UI の問題を切り出して、「修正前 ↔ 提案」を番号付きで並べた HTML 提案に落とす。**このスキルはコードを変更しない。** 提案で止め、ユーザーが採用番号を選んでから、初めて別途実装に入る。

このスキルは「頭脳」を自前で持たない**オーケストレーター**である。批評の観点と改善案の設計は、下記2つの上流スキルに委譲する。このスキル自身が担うのは、どちらの上流にも無い骨格 —「実物を開く／実測で裏取り／番号付き before-after 成果物／承認で止まる」— だけ。

## 委譲する2スキル（必須）

作業に入る前に、両方を Skill ツールで起動してから進める。

- **REQUIRED SUB-SKILL: `design:design-critique`** — 批評の 5 観点フレーム（第一印象／ユーザビリティ／視覚階層／一貫性／アクセシビリティ）はこのスキルの定義に従う。**Step 5 の直前で必ず起動する。**
- **REQUIRED SUB-SKILL: `frontend-design:frontend-design`** — 改善案（after）の設計はこのスキルの原則で駆動する。既存トークンを微調整するだけの“テンプレ修正”に逃げず、意図的で非テンプレな打ち手を作る。**批評（Step 5）でも「これは AI デフォルトに見えないか」の眼として使い、提案（Step 7）では after 設計の駆動役として使う。**（Skill ツールでは正確なスラッグ `frontend-design:frontend-design` を指定する。以降の本文では「frontend-design」と略記。）

## なぜこの形か

- **実物を見る**: className を読むだけでは、実際のコントラスト比・折返し・空状態・行の識別性は分からない。批評は必ずレンダリング結果に対して行う。推測で直すと外す。
- **提案は業務タスク起点で作る**: 過去の実運用では「重大」とした構造変更級の提案ほど不採用だった（業務フローの推測が外れていた）。一方、採用されたのは小粒のリント系ばかりで「浅い」印象を作った。指摘のネタ元は**画面の見た目の走査ではなく、主業務タスクを実際に歩いたときの摩擦**に置く。
- **確定済みの設計判断は前提**: 意図して作られたもの（例: Tooltip プリミティブまで用意した高密度の状態アイコン列）を「定石と違う」だけで覆す提案は即不採用になる。メモリ・規約・git 履歴から確定判断を先に集め、異議があれば番号提案ではなく質問として出す。
- **主張は実測で裏付ける**: 「コントラストが低い」「余白が過大」「重複でスキャンしづらい」は、数値がないと水掛け論になる。ブラウザに計測スニペットを注入して WCAG コントラスト比・行高・空値の色・重複件数を測り、**測った事実だけを断定**する。測っていない印象は「印象」として区別して書く。これは上流2スキルに無い、この骨格固有の強み。
- **批評と提案の頭脳は上流に委譲する**: 5 観点フレームは `design:design-critique`、改善案の設計品質は `frontend-design` が一次情報。ここで独自フレームを再定義しない（重複は劣化を招く）。critique-framework.md は「実測・深刻度・画面横断の一貫性」という**上乗せ層**だけを持つ。
- **提案は「修正前 ↔ 提案」の対比で見せる**: 文章の羅列より、簡略化した before/after モックアップを横に並べる方が、問題と打ち手が一目で伝わる。実装コストの判断もしやすい。
- **番号を振って止まる**: 一度に全部直すのではなく、ユーザーが番号で取捨選択できるようにする。実装との境界を明確にし、合意の上で進める。

## ワークフロー

### Step 1: 対象と到達手段を確定する

何を・誰のために・どの段階（探索/refine/最終）かを掴む。対象画面（URL や画面名）が曖昧なら確定させる。複数画面（マスタ群・一覧群など）の横断レビューなら、その一覧を先に列挙する。

ブラウザを開く手段は環境にあるものを使う（アプリ内ブラウザのプレビュー、または接続済みの Chrome 等）。ログインが要る画面で認証情報が不明なら、**推測せずユーザーに聞く**。開発既定の URL・ポート・ログイン手段がプロジェクトのメモリ/README にあれば従う。

### Step 2: 確定済みの設計判断を集める

画面を開く前に、プロジェクトのメモリ（MEMORY.md とリンク先の該当メモ）・CLAUDE.md の UI/デザイン方針・対象画面ディレクトリの `git log --oneline -15 -- <path>` を読み、**「確定済みの設計判断」を出典付きの箇条書き**にする。過去にこのスキルの提案が不採用になった記録・「〜する提案は却下された」類のメモも確定判断として扱う。

この一覧は批評の制約になる。確定判断と衝突する指摘は、Step 5 の番号提案ではなく Step 7 の「確認したい論点」に回す（覆したい根拠があるなら、それは提案ではなく質問の形で出す）。

### Step 3: 画面ごとに、主業務タスクを歩く

各画面で最初に**主業務タスク（ユーザーがこの画面で最も頻繁に完遂する操作）を1文で書く**。次にそのタスクを最初から最後まで実際に操作し、途中の摩擦 — 必要だったクリック/ホバー/スクロールの回数、迷った箇所、その場で読み取れずどこかを開いて確かめた情報 — を時系列でメモする。**このメモが提案の主なネタ元**で、静的な見た目の走査（スクリーンショット・`read_page` での構造把握・「2秒で最初に目が行く要素は正しいか」）はその補助。詳細パネルやモーダルなど主要インタラクションも実際に開いて挙動を見る。

### Step 4: 実測で裏取りする

`assets/measure.js` の中身をブラウザの JavaScript 実行ツールで注入する（このスニペットは oklch など任意の CSS 色を canvas 経由で sRGB に変換してから WCAG コントラスト比を出すので、`getComputedStyle` の色文字列を直接 RGB と誤読しない）。返る JSON から、本文/副題/プレースホルダ/主ボタンのコントラスト比、行高、空値（—/-/N/A 等）の色と本文との差、テーブル第1列の重複ラン、主ボタンの位置などを得る。

**実測は Step 3 で見つけた摩擦の裏付けに使う。** measure.js が返すキーの一覧を眺めて指摘を起こすと、毎回同じ種類のリント指摘（コントラスト・空値・重複…）が並ぶ提案になる — ネタ元はタスクの摩擦、実測はその証拠。断定する主張には対応する数値を添える。WCAG AA の目安は本文 4.5:1・大きい文字 3:1。合格しているものは**強みとして明記**する（批評は良い点の指摘も含む）。詳しい計測レシピは `references/critique-framework.md`。

### Step 5: 批評する（design-critique の5観点 × frontend-design の眼 × 実測）

先に **`design:design-critique` を Skill ツールで起動**し、その 5 観点フレームで各画面を評価する。その上に、このスキル固有の層を重ねる（詳細は `references/critique-framework.md`）:

1. **業務タスクへの効き**: 番号提案にする指摘は、**「どの業務タスクのどの操作が、どう速く/確実になるか」を1行で言えるもの**。タスクに紐づかない見た目の指摘（色・余白・語彙のリント系）は、全部まとめて1項目に束ねる。
2. **frontend-design の眼**: 各要素が「この題材のための選択」か、それとも「どの画面でも出てくる AI/テンプレのデフォルト」かを問う。テンプレ臭い箇所（意味の無い 01/02/03、汎用ヒーロー、既製色）は、それ自体を指摘対象にする。
3. **実測の裏付け**: Step 4 の数値を指摘に添える。壊れている問題（コントラスト不合格・重複・取り違え＝客観）と好みの問題（taste）を分けて書く。
4. **深刻度と優先順位**: 各指摘に 🔴重大 / 🟡中 / 🟢軽 を付け、「まず直すべき順」に並べ替える。🔴は**タスクの阻害が観察・実測で裏付けられているもの**に限る（見た目の定石違反だけでは🔴にしない）。

指摘は具体的に（「CTA がナビと競合している」＞「レイアウトが分かりにくい」）、なぜダメかを設計原則やユーザーの目的に結び付け、打ち手の方向性まで書く。複数画面レビューでは**一貫性が最重要級**（既に良い画面のパターンを他へ横展開する提案が効きやすい）。

### Step 6: 構造変更級の提案は、業務仮説を確認してから載せる

レイアウトの軸・ナビゲーション・列構成・情報の持ち方を変える提案は、必ず**前提となる業務仮説**（例:「配車で一番多い操作は車同士の空き比較である」）に立っている。HTML を書く前に、その仮説を明文化し、**AskUserQuestion 1回（最大3問、推奨案を先頭に）**で確認する。確認が取れた仮説に基づく構造変更だけを番号提案に載せ、確認できなかった・外れた仮説の案は捨てるか「確認したい論点」に回す。構造変更を含まない回はこの Step をスキップしてよい。

### Step 7: 「修正前 ↔ 提案」の after を設計し、HTML に落とす

**after を作る前に `frontend-design:frontend-design` を Skill ツールで起動**し、その原則（意図的な配色・タイポ・構造、テンプレ回避、題材に根ざした signature）で各打ち手を設計する。既存デザインシステムの資産（詳細パネル・ツールチップ・弱調/ピル等）が使えるならそれを横展開しつつ、**「既存トークンを少し動かすだけ」の安全牌に丸めない** — なぜその打ち手が題材に対して正しいのかを一言で言える粒度まで詰める。

設計できたら `assets/proposal-template.html` を土台に HTML 化する（テーマ追従・番号付き・before/after 2カラムの CSS を同梱済み）。テンプレの `<!-- ITEM -->` 例を複製し、1項目 = 番号 / タイトル / 対象画面 / 深刻度 / **効く業務タスク（1行）** / 「なぜ」/ before モックアップ / after モックアップ / 変更点の脚注 を埋める。件数は 5〜7 件まで — 少なく深い方が採用される。

番号提案の後に**「確認したい論点」節**（番号なし・質問形）を置く。ここに入るのは: (a) 確定済みの設計判断（Step 2）と衝突するが見直す価値がありそうな点、(b) Step 6 で確認できなかった業務仮説に基づく構造案。「今は〜という設計だと理解しています。もし〜なら…も検討できます — 実態はどちらですか?」の形で書く。

モックアップは**生スクショの貼付ではなく、要点だけ再現した簡略 HTML** にする（論点を圧縮でき、after を具体的に見せられる）。配色は同梱の CSS 変数を使い、ライト/ダーク両方で全テキストが読めることを出力前に自己チェックする。

作った HTML はファイルに書き、`Artifact` で公開する（環境に Artifact が無ければ、その HTML ファイルパスを提示）。深刻度の高い順に並べる。

### Step 8: 止まって番号を待つ

**ここでコードは変更しない。** 本文の結論（今回のまとめ＋指摘の表）はチャットにも書き、HTML はその要約・補強とする。「採用したい番号を教えてください（例: 2と3 / 全部）」と促す。番号を受け取ってから初めて、別途実装フェーズに移る。

## 出力契約（守る点）

- **批評は `design:design-critique`、提案は `frontend-design` を必ず起動した上で書く**（自前フレームだけで済ませない）。
- 番号提案の各項目は「効く業務タスク」を1行で言える。タスクに紐づかないリント系の指摘は束ねて1項目まで。
- 確定済みの設計判断（Step 2 の一覧）と衝突する案、および未確認の業務仮説に基づく構造変更は、番号提案ではなく「確認したい論点」に置く。
- 実測していない数値は書かない。断定と印象を区別する。
- 良い点も必ず挙げる（批評は否定の列挙ではない）。
- 提案は必ず番号付きで、before/after を対で見せる。after はテンプレ微調整に逃げない。
- コードは変更しない。実装は番号確定後に別途。
- 結論はチャット本文にも書く（HTML/アーティファクトだけに埋めない）。

## バンドル資産

- `assets/measure.js` — ブラウザ注入用の実測スニペット。任意の色を sRGB 化して WCAG コントラストを計算し、主要素の色・サイズ・位置・重複・空値表現を JSON で返す。`window.__ui` に `toRGB` / `contrast` / `effBg` ヘルパも生やすので、追加計測はそれを使う。
- `assets/proposal-template.html` — 「修正前 ↔ 提案」提案ページの雛形。テーマ追従の CSS 変数・番号バッジ・深刻度ピル・2カラム比較・脚注のスタイルを同梱。1項目分の例入り。
- `references/critique-framework.md` — `design:design-critique` の 5 観点に**上乗せする層**（確定判断の集め方、業務タスク起点の指摘づくり、深刻度の付け方、measure.js の読み方、frontend-design の眼を使ったテンプレ検出、良い/悪い指摘の言い換え）。5 観点そのものの定義は持たず、上流スキルに委ねる。
