# 批評の上乗せ層と計測レシピ

SKILL.md の Step 2〜7 の詳細。**5 観点フレームそのもの（第一印象／ユーザビリティ／視覚階層／一貫性／アクセシビリティ）は `design:design-critique` の定義に従う** — ここでは再定義しない。このファイルは、その 5 観点の上に重ねる層（文脈整合・業務タスク起点・実測の裏付け・frontend-design の眼・深刻度と優先順位）と、指摘の言い換え・提案 HTML の作法を規定する。

## 上乗せ層 0: 確定済みの設計判断を制約にする

批評の前に、次の3つから「意図して今の形になっているもの」を出典付きで集める:

1. **プロジェクトメモリ**: MEMORY.md の一覧と、UI/デザインに触れるメモ本体。「〜する提案は却下された」「〜が既定」類は最優先の制約。
2. **CLAUDE.md / 規約ファイル**: UI 密度・コンポーネント規約（共通プリミティブ・パターン）の記述。
3. **git 履歴**: `git log --oneline -15 -- <対象画面のディレクトリ>`。直近で作り込まれた箇所は「未整理」ではなく「決定直後」の可能性が高い。

扱い方: 確定判断そのものは番号提案で覆さない。**「定石と違う」は覆す理由にならない**（定石側が高密度業務 UI の実情に合っていないことも多い）。それでも見直す価値があると考える場合は、「確認したい論点」節で*質問*として出す — 「今は〜という意図の設計だと理解しています。もし〜であれば…も検討できますが、実態はどちらですか?」。

確定判断の**対象コンポーネント・列に触れる**番号提案（維持＋拡張の形を含む）は、脚注に「確定判断との整合」を1行で明記する — 何を維持し、何を変えないか（例:「DocumentStatusIcons と Tooltip は廃止せず維持。拡張のみ」）。明記できない案は論点側に回す。

## 上乗せ層 0.5: 指摘は業務タスクの摩擦から起こす

各画面で主業務タスクを1文で書き、実際に最後まで操作して摩擦を時系列でメモする（SKILL.md Step 3）。番号提案にできるのは、**「このタスクのこの操作が、こう速く/確実になる」を1行で言える指摘だけ**。言えない指摘は (a) リント束ね項目に入れる、(b) 捨てる、のどちらか。

- 摩擦の例: 判断に必要な情報がホバーやパネル開閉を要した／同じ操作を件数分繰り返した／目当ての行を探すのに全行を舐めた／入力の既定値が毎回手修正だった。
- 構造変更級の打ち手（レイアウトの軸・列構成・ナビの変更）は、前提の業務仮説を明文化して AskUserQuestion で確認してから番号に載せる（SKILL.md Step 6）。確認前に「重大」として最上段に置かない。

## 上乗せ層 1: frontend-design の眼でテンプレを検出する

`design:design-critique` の 5 観点は「その画面が破綻していないか」を見る。ここに `frontend-design` の視点を重ね、「その画面が**この題材のための選択**になっているか、どの画面でも湧いて出る AI/テンプレのデフォルトに留まっていないか」を問う。

テンプレ臭のサイン（見つけたら指摘対象にする）:

- 意味の無い連番マーカー（01 / 02 / 03）が、実際には順序を持たない要素に付いている。
- 汎用ヒーロー（大きな数字＋小さいラベル＋グラデ差し色）を、題材と無関係に反射的に使っている。
- 既製の色・角丸・影を、題材から導いた根拠なく採用している。
- コピーが「Submit」「送信」のようにシステム都合で、操作の結果を語っていない。

打ち手は「トークンを少し動かす」ではなく、**なぜその案が題材に対して正しいのかを一言で言える**粒度まで詰める（after 設計時に `frontend-design` を起動するのはこのため）。

## 上乗せ層 2: 深刻度の付け方

- 🔴 **重大**: 主業務タスクの阻害が**観察・実測で裏付けられている**（例: タスク完遂に必須の比較が画面上でできない、コントラスト不合格で読めない）。見た目の定石違反・未確認の業務仮説に基づく構造案は、実害の裏付けが無い限り🔴にしない。
- 🟡 **中**: 一貫性・密度・導線の明確さ。単体では致命的でないが、積むと使い勝手を損なう。
- 🟢 **軽**: 仕上げ・可読性・語彙統一。あると良い。リント束ね項目はここ。

**壊れている問題（客観）と好みの問題（taste）を分ける。** コントラスト不合格・操作の取り違え・重複は客観。角丸の大きさや色味の好みは taste で、そう明記する。段階（探索/最終）に批評の粒度を合わせる — 早い探索に最終仕上げの指摘をぶつけない。

複数画面の横断レビューでは **一貫性が最重要級**。「同じ種類の画面が同じ作法に見えるか」を軸に、既に良い画面のパターンを他へ横展開する提案が効きやすい。

## 上乗せ層 3: measure.js で実測して裏付ける

注入すると JSON を返す。主なキー:

- `textContrast.min` / `worst5` / `belowAA` — 本文テキストの最小コントラストと AA 未満の要素数。`belowAA > 0` なら客観的なアクセシビリティ指摘になる。合格なら強みとして書く。
- `buttons[]` — 各ボタンの `contrast` / `filled`(塗りか) / `pos`。`filled:true` が複数あり位置が散っていれば「主 CTA の競合」を疑う。
- `table.maxConsecutiveSameFirstCol` — 第1列が連続で同じ値のラン。大きい（例 ≥5）なら「重複でスキャンしづらい / グループ化余地」。`distinctFirstCol` と `rowCount` の比も参考。
- `table.rowHeight` — 行高。業務系で過大なら密度改善余地。
- `emptyValue` — 空値グリフの色。本文と同等に濃い（コントラストが高い）なら「空値を弱調」提案の根拠。

個別要素はブラウザで `__ui.contrast(getComputedStyle(el).color, __ui.effBg(el))` を叩いて追加計測できる。**断定する主張には必ず対応する数値を添える。** 測っていない印象は「印象」と明示して区別する。

**役割の向き**: 実測はタスク摩擦（上乗せ層 0.5）の裏付けであって、指摘の生成源ではない。上のキー一覧を上から舐めて「該当したもの」を提案リストにすると、どの画面でも同じ種類のリント指摘が並ぶ — その場合はタスク歩行に戻る。

WCAG AA 目安: 本文(24px 未満かつ 18.66px 未満・bold でない) 4.5:1、大きい文字 3:1。タッチターゲットは概ね 44px を目安に（マウス主体の業務デスクトップは 32px 程度も許容、と文脈で判断）。

## 指摘の言い換え（具体 > 抽象）

- ✗「レイアウトが分かりにくい」→ ✓「主 CTA『登録』が右上ナビの色と同じで競合し、最初に目が行かない」
- ✗「余白を調整すべき」→ ✓「フィルタカードの縦が 358px あり、他画面の一段バー(約 56px)と不揃い。一段に集約して縦を節約」
- ✗「見づらい」→ ✓「在庫 0 が実在庫と同色・同ウェイト(いずれも #0a0b0d / 600)で、在庫のある行が埋もれる。0 を弱調」

必ず **なぜダメか（原則・ユーザー目的）** と **打ち手（代替案）** をセットにする。良い点も挙げる（「台帳の符号色分けは明快」等）。批評は否定の列挙ではなく、伸ばす所と直す所の両方を示すもの。

## 提案 HTML の作法

- after の設計は `frontend-design:frontend-design` を Skill ツールで起動してから行う（テンプレ微調整に丸めない）。
- `assets/proposal-template.html` の `<!-- ITEM -->` を複製。深刻度の高い順。件数は 5〜7 件まで。
- 各項目の冒頭に「効く業務タスク」を1行で書く（`.task` スロット）。
- 番号提案の後に「確認したい論点」節（番号なし・質問形）。確定判断への異議・未確認仮説の構造案はここ。空なら節ごと省く。
- before は「今こうなっている」を、after は「打ち手」を、要点だけ簡略再現。生スクショは貼らない（論点が拡散する）。
- 脚注 `.foot` に「変更点」を実装の当たりが付く粒度で書く（どのクラス/どの表示を変えるか）。
- 既存デザインシステムの資産（詳細パネル・ツールチップ・弱調/ピル等）が使えるなら、それを横展開する形にすると実装コストが低く一貫性が上がる — その旨を脚注か凡例に添える。
- 出力前チェック: ライト/ダーク両方で全テキストが読めるか。結論はチャット本文にも書く。
