# 判断書（siji-decision-sheet）

## 概要

判断論点を「1論点=1カード」で並べ、ページ下部の回答バーで答えを収集する HTML アーティファクト。
ユーザーは各カードで選択肢を選ぶ → 下部の回答行が連動して更新される → コピーしてチャットに
貼ると回答が確定する。**未選択のカードは「スキップ」（今回は決めない）を意味する**。
推奨どおりで良い分は「残りを推奨で埋める」ボタンで一括選択できる。

**使うかどうかを論点の件数で決めない。1件だけでも、原因・証拠・複数案の帰結の比較といった
説明が要るならこのスキルを使う。** AskUserQuestion で直接聞くのは、選択肢を読めばその場で
決まり、根拠を示す必要がない確認に限る。**AskUserQuestion は判断書を出さないときの手段で
あって、判断書とは併用しない**（→「回答の収集と解釈」）。
**AskUserQuestion で直接聞く場合も、質問文・選択肢の書き方は本スキルの判断カードの規律
（疑問文・読み手基準の語彙・「操作 → 結果」のシナリオ）に従う**。ただしカードの構成
（背景・前提の節立て）をダイアログに持ち込まない。質問文は「状況がわかるシナリオ 1〜2 文 +
疑問文 1 文」に圧縮する。
セッション開始直後の実装前インタビューは、読み手との共有知識が依頼文と画面の挙動しかない
最も迷子が起きやすい場面なので特に厳守する。

## 出力の構成（この順で）

1. **ヘッダ** — 判断件数と「これを決めれば何が進むか」を1文で。
2. **判断カード**（判断が要るものだけ。1論点1カード）
   - **並び順 = 影響範囲の大きい順**。致命 → 重要 → 中で並べ、同じ重要度なら手戻りコストの
     大きいほうを上にする。**ID は並び順どおりに振る**ので `1` が常にその判断書の最重要。
     途中で論点が増えたら番号を振り直して順序を保つ（ユーザーは上から読んで途中でやめる前提）。
   - `1` 形式の ID（数字）+ 重要度バッジ + **疑問文のタイトル**（「〜するか?」「どちらに寄せるか?」。
     名詞句にしない。何を決めるのかがタイトルだけで伝わるようにする）。この順に置くと左端に
     「1 致命」が縦に揃い、上から拾い読みして重要度を追える。バッジの基準:
     - **致命** = 誤ると巻き戻しが難しい（データ・公開 API・セキュリティ・本番影響）
     - **重要** = 仕様・UX に目に見える影響が出る
     - **中** = 内部品質・保守性・好みの範囲
   - **背景**: 1〜2文。証拠や規定に入る前に「何の仕組みの話か」を、チャットを読んでいない人にも
     通じる日常語で置く。専門語・固有名はここで一言説明する
   - **前提**: 判断に使う事実を 2〜4 行の箇条書きで。意見・推奨の先取りは書かない。書き方:
     - 1 行 1 事実の単文。証拠（`ファイル:行`・実測値）は文中に挟まず行末に置く
     - 読み手基準の語彙で書く。読み手がその時点で知っていること（依頼文・画面で見える挙動・
       カード内で説明済みの語）だけを前提知識とし、「使う人から見るとこうなる」から書き始める。
       内部実装の識別子は行末の証拠にとどめ、チャット内でしか通じない語・相対参照（「今日の」
       「上記の」）を使わない
   - **具体例**: 「操作 → 結果」のシナリオを1文。前提の箇条書きには入れず、`具体例` ラベルの
     独立した行に出す（役割が違うので、前提の事実と混ぜない。行頭記号で区別しようとすると、
     その行だけ本文の開始位置がずれる）。コードレビューの失敗シナリオと同じ型。例: 「在庫切れの
     商品を注文すると、その場でエラーになり注文が保存されない」。不具合の無い選択形の
     論点では「この判断が問われる場面」を書く
   - **選択肢**: **推奨1 + 対案2つ以内 + その他（自由記述）**。`A.` `B.` の大文字で並べる
     （論点の ID が数字なので、回答行の `1(スラッグ)=A` で番号と回答が数字どうしにならない）。
     推奨は先頭に置き「推奨」タグを付けるが、**ラジオはどれも checked にしない**（未選択=
     スキップの意味論を壊さない）。対案が3つ以上欲しくなったら、論点が2つ混ざっていないか
     疑って分割する。
   - **推奨理由**: 1〜2文。**推奨案の選択肢の中**に書く（カード末尾に切り出すと、どの案の話か
     読み手が戻って確かめることになる）
3. **修正一覧**（あれば）— 直し方が一意に決まる修正は判断カードにせず表にまとめる。
   **この表も影響範囲の大きい順に並べる**（判断カードと同じ基準。読み飛ばされるのは下の行）。
   行番号は `1` から振るだけで、ID は付けない。判断カードはユーザーの負担なので増やさない。
   **この表は判断書の提示と同時に着手してよい**（判断書が着手宣言を兼ねる）。ただし判断カードの
   結論次第で内容が変わる行は、その旨を表に明記して回答まで保留する。
4. **回答バー**（ページ下部・sticky）— `1(スラッグ)=A 2(…)=スキップ` 形式の回答行が
   ラジオ選択と連動して更新される。カウンタ・「残りを推奨で埋める」ボタン・「コピー」ボタンを置く。
   カウンタは**スキップを未回答として数えない**（「決定 2件 ・ スキップ 1件」、全件未選択なら
   「3件ともスキップ（このまま返すと全件見送り）」、全件選択済みなら「3件とも決定」）。
   「0件 回答済み」と出すと、スキップを催促しない方針と表示が食い違う。

## 論点が画面に関わるとき

判断の対象が画面の見た目・操作・導線を含むなら、カードを書き始める前に次の2つを済ませる。

**決定済みの方針を出典付きで集める。** プロジェクトメモリ（「〜する提案は却下された」「〜が既定」類）・
CLAUDE.md の UI 方針・対象画面のディレクトリの `git log --oneline -15 -- <path>` から、
意図して今の形になっているものを拾う。直近で作り込まれた箇所は「未整理」ではなく「決定直後」の
可能性が高い。集めたものは前提の制約になる。**確定済みの方針と衝突する案は選択肢に混ぜない** —
独立した判断カードにして「今は〜という意図の設計だと理解しています。もし〜なら…も検討できますが、
実態はどちらですか?」の形で問う。**「定石と違う」は覆す理由にならない**（定石側が高密度な業務画面の
実情に合っていないことも多い）。

**画面を実際に開いて確かめてから前提を書く。** クラス名やコードを読むだけでは、実際のコントラスト比・
折り返し・空状態・行の識別性は分からない。ブラウザを開く手段は環境にあるものを使い（プレビュー、
接続済みブラウザ等）、その画面で最も頻繁に完遂される操作を最初から最後まで歩く。論点はその途中で
起きた摩擦から起こす — 必要だったクリックやホバーの回数、迷った箇所、その場で読み取れずどこかを
開いて確かめた情報。

数値の裏取りには `${CLAUDE_PLUGIN_ROOT:-$HOME/.claude}/skills/siji-decision-sheet/references/measure.js`
の中身をブラウザの JavaScript 実行ツールに注入する（任意の CSS 色を canvas 経由で sRGB に正規化
してから WCAG コントラスト比を出すので、`getComputedStyle` の色文字列を直接 RGB と誤読しない）。
WCAG AA の目安は本文 4.5:1・大きい文字 3:1。前提に書く実測値は、**行末の証拠として `measure.js` の
キー名と値を置く**（例: `textContrast.min 3.1:1`、`table.maxConsecutiveSameFirstCol 7`）。
画面を開けない環境では、その行末に「未実測」と書く。

**実測は裏取りであってネタ元ではない。** 返る JSON のキーを上から舐めて該当したものを論点にすると、
どの画面でも同じ種類の指摘（コントラスト・空値・重複…）が並ぶ。論点は操作の摩擦から起こし、実測は
その証拠に使う。同じ種類の論点ばかり並んだら、画面を歩き直す合図。

## 判断書のライフサイクル

- **1判断バッチ = 1ファイル**。ファイル名にトピックを含め（例: `decision-auth-flow.html`）、
  過去の判断書のファイル名を使い回さない（Artifact は同一パスへの再公開で上書きされ、
  回答済みの判断書が消える）。
- **ID = 判断書内の連番（数字）で、各判断書で必ず 1 から**。番号だけでは判断書をまたいだ
  区別が付かないので、**同じ会話で2枚目の判断書を出す前に、1枚目の回答を必ず回収する**。
  未回収の判断書が2枚並ぶ状況を作らない（`1=A` がどちらの判断書への返答か決められなくなる）。
  やむを得ず重ねるときは、ヘッダで「◯◯の件の判断書」と主題を書き分け、回答を求めるときも
  主題つきで聞く。

## 実装

- [references/template.html](references/template.html) をベースに内容を差し替える。
  回答バーの連動 JS・推奨一括ボタン・clipboard フォールバック・ライト/ダーク対応は実装済み。
- コピーボタンは `navigator.clipboard` → `execCommand("copy")` → 選択のみ、の3段で試す。
  段を減らさない（Artifact の iframe では1段目が Permissions Policy で塞がれることがあり、
  そこで諦めるとユーザーが毎回手で ⌘C を押すことになる）。
- カードの構造は `data-id` / `data-slug` / `name=<ID>` / 推奨ラジオの `class="rec"` の対応を
  崩さない（回答行の生成と一括ボタンが壊れる）。
- 重要度はカードの `data-sev`（`crit` / `high` / `med`）だけで指定する。左帯とバッジの色は
  そこから決まるので、バッジ側に色クラスを足さない（2箇所がずれる）。
- 背景・前提・具体例は `<div class="field"><span class="lbl">ラベル</span>本文</div>` で書く。
  ラベルだけが淡色（`--muted`）で、本文は読ませる色（`--ink-2`）になる。本文側に
  `--muted` を当てない（判断書全体が薄く見える原因になる）。
- **本文に行頭記号（`・` `→` など）を置かない。** ぶら下げインデントが入ると、その行の文字
  だけ他の本文より右にずれて「揃っていない」ように見える。役割が違う行は記号ではなく独立した
  ラベル行に出す。ラベルを本文と同じ行に置くのも同じ理由で不可（1行目だけずれる）。
  デスクトップではラベル列とラジオ列を同じ幅にしてあるので、背景・前提の各行・具体例・
  選択肢名・選択肢の説明・推奨理由が**カード全体で1本に揃う**。狭い画面ではラベル列だけが
  畳まれるため、読む側と選ぶ側でラジオぶんの差が残る（地の色が分かれているので許容する）。
- 推奨理由は推奨案の `.opt` の中に
  `<span class="owhy"><span class="olbl">推奨理由</span>…</span>` として置く。
- カードは「読む材料＝淡い地（`.top` / `.why`）、選ぶところ＝素地（`.opt`）」で塗り分けてある。
  この対応を崩すと、どこから操作なのかが読めなくなる。
- 本文の折り返し幅は `--measure` に集約してある。個別に `max-width` を足さない
  （要素ごとに折り返し位置がずれるのが、行が追いにくくなる最大の原因）。
- 選択肢は `<div role="radiogroup" aria-labelledby="dtitle-<ID>">` で囲み、論点タイトルの
  `<span class="dtitle">` に `id="dtitle-<ID>"` を振る。これが無いと読み上げで選択肢の文言
  だけが読まれ、どの論点のものか伝わらない。
- その他の自由記述は `<textarea class="other-text" rows="1">`。入力量に応じて高さが伸びる。
  `input type="text"` に戻さない（長い記述が1行に押し込まれ、書いた本人が読み返せなくなる）。
- 回答バーのカウンタと一括ボタンのラベルは `sync()` が状態から組み立てる（件数・disabled も）。
  文言を静的に書き戻さない。
- Artifact で公開する（`artifact-design` の読み込みは Artifact 側の必須手順に従う）。
  favicon は `📋` で固定し、title は再公開しても変えない。

## 回答の収集と解釈

- **判断書を公開したターンは AskUserQuestion を呼ばずに終了し、貼り付け回答を待つ**。
  判断書で既に問うている論点をダイアログでも聞けば二重質問になる。論点の件数によらず例外なし。
- 回答の受け口は 2 つだけ:
  1. 判断書下部の**回答バーをコピーして貼る**
  2. **本文に書いた回答テンプレ1行**に直接返す
     （例: `1(スラッグ)=A 2(スラッグ)=スキップ 3(スラッグ)=B`）。
     判断書を開かずにチャットだけで返せる逃げ道として必ず本文にも書く。
- **言及されなかった論点はスキップとして扱う**（`1=A 3=B` だけ来たら 2 はスキップ）。
  スキップは「今回は決めない」という有効な回答であり、催促や聞き直しをしない。
- 回答受領時は確定分とスキップ分を1行で復唱してから作業に入る
  （例: 「確定: 1=A, 3=B / スキップ: 2」）。復唱への訂正が来たら上書きする。
- **スキップされた論点は保留リストにする**: それに依存する変更は現状維持のまま確定分だけ
  進め、次の判断機会（次の判断書、実装後の確認）で再提示する。
- 決定の記録先は次の優先順位で選ぶ: issue 駆動フローがあれば issue 本文の「決定事項」表 →
  プロジェクトの設計ドキュメント（`docs/` 等）→ どちらも無ければ会話内の復唱のみで良い
  （記録のためだけにファイルを新設しない）。

## よくある失敗

| 失敗 | 対処 |
|---|---|
| 論点が1〜2件だからと AskUserQuestion で済ませる | 件数は基準ではない。証拠や案の比較を示さないと決められない論点なら、1件でも判断書を出す |
| 判断書の公開後に AskUserQuestion でも同じ論点を聞く | 二重質問。判断書を出したターンはダイアログを開かず、回答バーのコピペか回答テンプレへの返答を待つ |
| ラジオを checked にして出す | 未選択=スキップの意味論が壊れる。推奨は `rec` クラス+「推奨」タグで示し、選択はユーザーに委ねる |
| スキップを回答漏れ扱いして聞き直す | スキップは有効な回答。保留リストに落とし、確定分だけ先に進める |
| 判断不要の修正まで判断カードにする | 直し方が一意なら修正一覧の表へ。カードが増えるほど回答されなくなる |
| 1枚目が未回答のまま2枚目の判断書を出す | ID は両方 `1` から始まるので `1=A` がどちらへの返答か決められない。先に回答を回収する |
| 選択肢を `1.` `2.` の数字で並べる | 回答行が `1(スラッグ)=1` になり論点番号と回答を読み違える。選択肢は `A.` `B.` |
| 前提やシナリオに `・` `→` の行頭記号を付ける | ぶら下げインデントでその行だけ文字が右にずれ、カード全体が「揃っていない」ように見える。記号を足さず、役割が違う行は独立したラベル行に出す |
| 見つけた順・書きやすい順に並べる | 上から読んで途中でやめられる前提。影響の大きいものが `1`、軽いものほど下 |
| 対案を3つ以上並べる | 論点が2つ混ざっているサイン。分割するか対案を2つに絞る |
| タイトルを名詞句で書く | 「検証方法」では何を決めるのか分からない。「どこまでテストするか?」のように疑問文にする |
| 前提に意見・推奨の先取りを混ぜる | 前提は事実だけ。評価は選択肢の帰結文と推奨理由に書く |
| チャット内でしか通じない語で書く | 判断書は後から単体で読まれる。カード内で説明していない略語・相対参照を使わない |
| 内部実装の説明から書き始める | 読み手の共有知識は依頼文と画面の挙動だけ。「使う人から見るとこうなる」を先に置き、内部は行末の証拠に |
| 選択肢に根拠がない | 各選択肢に「選んだ場合に何が起きるか」を1文で書く。裏取りのない選択肢を並べない |
| その他（自由記述）を省く | 提示した選択肢が正しい保証はない。必ず逃げ道を付ける |
| 回答行に ID しか入れない | `1(通知の送信先)=A` のようにスラッグを含め、貼られた行だけで意味が通るようにする |
| 画面の論点で、決定済みの方針を調べずに選択肢を並べる | メモリ・CLAUDE.md・git log から先に集める。衝突する案は選択肢に混ぜず、別カードの質問にする |
| 画面を開かず、コードだけ読んで前提を書く | 実物を開いて操作してから書く。測っていない数値は書かず、その行末に「未実測」と記す |
