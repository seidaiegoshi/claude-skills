# 説明と報告の出し方

**このスキルの目的は、読み手の理解を最短にすること。成果物の体裁を整えることではない。**
説明の出し方（1〜6）と、報告に何を載せるか（7〜10）の実務基準。図を1枚でも描こうとしたら、
また説明・報告を書き始める前に、この基準で判断する。

判断に迷ったら「これは読み手が理解するのに要るか」に戻る。要らないなら足さない。

## 1. 図にする / しない

図はテキストより高コスト（トークン・読む側の注意）。**関係性が2次元的なときだけ**元が取れる。

**図にする:**
- 要素が3つ以上あり、その間に関係（矢印・包含・順序・分岐）がある
- 2案以上の比較で、軸が2つ以上ある（例: コスト × 保守性）
- 全体像を先に掴ませないと個別の説明が理解できない構造

**図にしない（YAGNI）:**
- 要素が1〜2個 / 単純な可否・Yes-No
- 一直線の手順で分岐がない（番号付きリストで足りる）
- コード断片・差分そのものを見せれば済む（図に描き起こさない）
- 事実の列挙で関係性がない（表で足りる）

迷ったら図にしない。図が出るのが当たり前になると、本当に必要な図の価値が下がる。

## 2. 図の型を選ぶ

| 説明したいこと | 型 |
|---|---|
| 処理の流れ・手順の分岐 | フロー図（ノード + 矢印、分岐はひし形） |
| モジュール/テーブルの依存 | 依存グラフ（矢印の向き = 依存の向き） |
| 案A/案Bの比較 | 並列カード（各案1カード、同じ見出し構成で揃える） |
| 分類・構成の階層 | ツリー / ネストしたボックス |
| 時系列・フェーズ進捗 | タイムライン（横軸に時間、完了/進行中/未着手を色分け） |
| ステータスの遷移 | ステートマシン（状態 = ノード、遷移条件 = 矢印ラベル） |
| 変更の影響範囲 | 依存グラフ + 変更点を強調色でハイライト |

型が決まらない = まだ自分が構造を理解していない。先に構造を言語化する。

## 3. 出し方を選ぶ（既定は HTML + Artifact）

| 内容 | 手段 |
|---|---|
| ノードとラベルだけで伝わるごくシンプルな図（フロー・状態遷移・依存グラフ） | `show_widget` |
| 説明文・表・コード・章立て・注釈を伴うもの（設計提案・比較検討・調査/分析レポート・レビュー結果・変更サマリ・実装計画） | HTML ファイル → `Artifact` |

- **既定は HTML + `Artifact`。`show_widget` は例外**。迷ったら HTML 側に倒す
- 図が主役に見えても、説明文が付くなら HTML の中に図（インライン SVG / mermaid）を埋め込んで1枚にまとめる
- 図の型の判断（セクション1・2）は手段に関わらず共通。HTML に埋める図も同じ基準で選ぶ
- HTML に図・画像を入れたら**クリックで拡大できるようにする**（貼り方はセクション9）

## 4. show_widget の作法

`show_widget`（インライン図解ツール）が使えるセッションだけの話。無ければセクション3の HTML + Artifact に寄せ、どちらも無ければセクション6に落とす。

- **初回呼び出し前に `mcp__visualize__read_me` を silent で呼ぶ**（CSS変数・配色・レイアウト規約を取得）。read_me を呼んだことはユーザーに報告しない
- 色は必ず取得した **CSS変数**で指定。ハードコードした hex はライト/ダークテーマで破綻する
- 背景は透過、トップレベルの padding は付けない
- `title` は具体的な snake_case。会話に図が複数出たときに区別できる名前にする（`diagram` ではなく `stock_consume_flow`）
- ラベル・注釈は**日本語**。コード識別子（モデル名・関数名）は原文のまま
- 情報量は1図1テーマ。全部を1枚に詰めない。2テーマあるなら2枚に割る

## 5. 図と本文の関係

- **図はテキストの要約であって置き換えではない。** 図を見なくても本文だけで結論が伝わる状態を保つ
- 図の直後に、その図から読み取ってほしい結論を1〜2文で書く
- 図に描いていない前提・例外・トレードオフは本文に書く（図は単純化されるので、そこに嘘が混じらないようにする）

## 6. HTML / show_widget が使えない環境

どちらも使えないセッションでは図を諦めず、Markdown で構造化する。

- 比較 → 表（軸を列、案を行）
- 階層 → ネストした箇条書き
- フロー → 番号付きリスト + 分岐は入れ子
- 依存 → 「A → B（B が A に依存）」の明示的な列挙

**「図にする条件」に該当したのに何も構造化しない**のが最悪の結果。手段が無いときほど本文の構造化で埋め合わせる。

## 7. 報告の構成

報告は文章を書く作業ではなく、**スロットを埋める作業**。何をした報告かでスロットが変わる。

### 実装作業を終えたとき

DB と画面のスロットは、その変更が今回の差分に含まれるなら埋まっていないと報告が完成していない。

| # | 節 | 埋めるのが必須になる条件 |
|---|---|---|
| 1 | 今回のまとめ | 常に。結論はチャット本文にも書く |
| 2 | 変更ファイル | 常に。パス + 1行の役割 |
| 3 | **DBの変更点** | 差分に migration・モデル定義・データ移行が含まれるとき |
| 4 | **画面キャプチャ** | 差分に画面の見た目・文言・導線の変更が含まれるとき |
| 5 | 検証結果 | 常に。実行コマンドと出力（生ログはチャット本文にも） |

### 提案・調査だけで終わるとき

コードを変えずに終わる報告（設計提案・調査結果・レビュー・比較検討）はこの4スロット。

| # | 節 | 内容 |
|---|---|---|
| 1 | 結論 | 何がわかったか / 何を勧めるか。1〜3行で**先に**置く |
| 2 | 根拠 | そう言える証拠。実測値・コマンド出力・該当箇所を貼る |
| 3 | 残る不確かさ | 確かめていないこと・置いた前提。書かないと読み手が過信する |
| 4 | 次の一手 | 決めてほしいこと、または次に走らせること |

判断を仰ぐ論点が含まれるなら、4を skill `siji-decision-sheet` の判断書に置き換える。

### 両方に共通

該当しない節は載せない。**該当するのに中身を出せなかったときは、節を消さずに1行で理由を書く**
（「dev server を起動できずキャプチャ未取得」など）。黙って落とすと、読み手は「変更が無かった」と
読む。

HTML にするかチャット本文だけにするかは規模で決まる（→ グローバル CLAUDE.md「コミュニケーション」）。
HTML にするなら、その中に置く図の判断はセクション1〜2に従う。

## 8. DBの変更点の書き方

差分の判定は `git status --short` に migration ファイルが出るか、`src/apps/models/` 等が
変わっているか。表の列は「対象（テーブル.列）／変更／NULL可否・既定値／既存行への影響／
データ移行」の5つ。

- 実際に流れる DDL は推測せず `python src/manage.py sqlmigrate <app> <番号>` で出す（DB 起動が必要）。
- **生成・適用の状態を必ず書き分ける**: 「マイグレーション未生成」「生成済み・未適用」「適用済み」。
  マイグレーションの生成・適用を人が手動でやる規約のプロジェクトでは、次に人が打つコマンドを載せる。
- ER 図を生成するプロジェクトなら、再生成した図の該当部分もこの節に置く。

## 9. キャプチャの撮り方と、図・画像の貼り方

**ブラウザペイン・Chrome MCP の screenshot はモデルの視界に返るだけでファイルにならない。**
Artifact に貼るには実ファイルが要るので、Playwright で撮ってファイルに落とす。

```bash
SP=<スクラッチパッド>   # プロジェクトに残さない
# このスキルの起動時に出る "Base directory for this skill" がスキルの絶対パス（配置場所に依らない）
VE=<Base directory>/references

# 1. 撮る。ログインが要る画面は E2E の storageState を使い回す
cd e2e && node "$VE/capture.cjs" \
  --base http://localhost:8002 --storage-state .auth/admin.json \
  --out-dir "$SP/shots" --shot 注文一覧:/orders --shot 在庫一覧:/stocks

# 2. 縮小して <img src="data:..."> を作り、報告 HTML に貼る
"$VE/embed.sh" "$SP/shots/注文一覧.png" --alt 注文一覧 >> "$SP/shots.html"

# 3. クリックで拡大できるようにする。報告 HTML の末尾に1回だけ貼る
cat "$VE/lightbox.html" >> "$SP/report.html"
```

- **図・画像を1枚でも入れたら `lightbox.html` を貼る**。縮小して埋め込んだ画像は本文の幅では読めず、
  拡大できないと証拠にならない。`embed.sh` の出力は自動で対象、インライン SVG・mermaid の図は
  `<figure data-zoom>` で包む。
- storageState が別サーバー向け（E2E 用 DB など）で使えないときは `--email` / `--password` で
  ログインし、`--save-state <path>` に保存すれば2回目以降は再利用できる。
- **チャット本文だけで報告する規模のとき**（1ファイルの小修正など）は data URI 化は不要。PNG を
  そのまま `SendUserFile` で添付する。
- ダークモードの見た目を報告するなら `--color-scheme dark`（既定は light）。
- 描画待ちは `--wait-for <セレクタ>`。**`networkidle` では待たない**（Vite の HMR が
  WebSocket を張り続けるので永久に来ない。capture.cjs は `load` + 要素待ちで実装済み）。
- **変更前を撮れないことは普通にある**（既に直した後に頼まれた等）。無理に再現せず「変更後のみ」と
  明記する。撮れるなら `git stash` して撮り、必ず戻す。
- Artifact のページ全体は 16MB 上限。`embed.sh` は既定で長辺 1200px・JPEG 品質 70 に落とすので
  1枚 100〜300KB に収まる。文字の潰れが問題なら `--width 1600 --quality 85`。

## 10. 報告のよくある失敗

| 失敗 | 直し方 |
|---|---|
| キャプチャの代わりに「〜のように表示されます」と書く | 実画面を撮る。撮れないなら理由を書く |
| DB 変更を「マイグレーションを追加しました」の1行で済ます | 列単位の表 + 適用状態まで書く |
| Artifact に外部 URL の画像を貼る | CSP で読めない。data: URI で埋め込む |
| 撮影を `networkidle` で待つ | Vite の HMR で永久に来ない。`load` + 要素待ちにする |
| キャプチャを全画面 PNG のまま埋め込む | 数 MB になる。`embed.sh` を通す |
| 画像を貼っただけで拡大できず、縮小版しか読めない | 末尾に `lightbox.html` を貼る |
| 確かめていないことを断定して書く | 裏を取った範囲だけ断定し、残りは「未確認」と明記する |
