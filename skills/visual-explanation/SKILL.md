# 説明の可視化（インライン図解）

図・ダイアグラム・チャートを出すときの実務基準。**図を1枚でも描こうとしたら、その前にこの基準で「本当に図が要るか」「どの型か」を判断する。**

## 1. 図にする / しない

図はテキストより高コスト（トークン・読む側の注意）。**関係性が2次元的なときだけ**元が取れる。

**図にする:**
- 要素が3つ以上あり、その間に関係（矢印・包含・順序・分岐）がある
- 2案以上の比較で、軸が2つ以上ある（例: コスト × 保守性）
- 全体像を先に掴ませないと個別の説明が理解できない構造

**図にしない（YAGNI）:**
- 要素が1〜2個 / 単純な可否・Yes-No
- 一直線の手順で分岐がない（番号付きリストで足りる）
- コード断片・差分そのものを見せれば済む（図に描き起こさない）
- 事実の列挙で関係性がない（表で足りる）

迷ったら図にしない。図が出るのが当たり前になると、本当に必要な図の価値が下がる。

## 2. 図の型を選ぶ

| 説明したいこと | 型 |
|---|---|
| 処理の流れ・手順の分岐 | フロー図（ノード + 矢印、分岐はひし形） |
| モジュール/テーブルの依存 | 依存グラフ（矢印の向き = 依存の向き） |
| 案A/案Bの比較 | 並列カード（各案1カード、同じ見出し構成で揃える） |
| 分類・構成の階層 | ツリー / ネストしたボックス |
| 時系列・フェーズ進捗 | タイムライン（横軸に時間、完了/進行中/未着手を色分け） |
| ステータスの遷移 | ステートマシン（状態 = ノード、遷移条件 = 矢印ラベル） |
| 変更の影響範囲 | 依存グラフ + 変更点を強調色でハイライト |

型が決まらない = まだ自分が構造を理解していない。先に構造を言語化する。

## 3. 出し方を選ぶ（既定は HTML + Artifact）

| 内容 | 手段 |
|---|---|
| ノードとラベルだけで伝わるごくシンプルな図（フロー・状態遷移・依存グラフ） | `show_widget` |
| 説明文・表・コード・章立て・注釈を伴うもの（設計提案・比較検討・調査/分析レポート・レビュー結果・変更サマリ・実装計画） | HTML ファイル → `Artifact` |

- **既定は HTML + `Artifact`。`show_widget` は例外**。迷ったら HTML 側に倒す
- 図が主役に見えても、説明文が付くなら HTML の中に図（インライン SVG / mermaid）を埋め込んで1枚にまとめる
- 図の型の判断（セクション1・2）は手段に関わらず共通。HTML に埋める図も同じ基準で選ぶ

## 4. show_widget の作法

`show_widget`（インライン図解ツール）が使えるセッションだけの話。無ければセクション3の HTML + Artifact に寄せ、どちらも無ければセクション6に落とす。

- **初回呼び出し前に `mcp__visualize__read_me` を silent で呼ぶ**（CSS変数・配色・レイアウト規約を取得）。read_me を呼んだことはユーザーに報告しない
- 色は必ず取得した **CSS変数**で指定。ハードコードした hex はライト/ダークテーマで破綻する
- 背景は透過、トップレベルの padding は付けない
- `title` は具体的な snake_case。会話に図が複数出たときに区別できる名前にする（`diagram` ではなく `stock_consume_flow`）
- ラベル・注釈は**日本語**。コード識別子（モデル名・関数名）は原文のまま
- 情報量は1図1テーマ。全部を1枚に詰めない。2テーマあるなら2枚に割る

## 5. 図と本文の関係

- **図はテキストの要約であって置き換えではない。** 図を見なくても本文だけで結論が伝わる状態を保つ
- 図の直後に、その図から読み取ってほしい結論を1〜2文で書く
- 図に描いていない前提・例外・トレードオフは本文に書く（図は単純化されるので、そこに嘘が混じらないようにする）

## 6. HTML / show_widget が使えない環境

どちらも使えないセッションでは図を諦めず、Markdown で構造化する。

- 比較 → 表（軸を列、案を行）
- 階層 → ネストした箇条書き
- フロー → 番号付きリスト + 分岐は入れ子
- 依存 → 「A → B（B が A に依存）」の明示的な列挙

**「図にする条件」に該当したのに何も構造化しない**のが最悪の結果。手段が無いときほど本文の構造化で埋め合わせる。
